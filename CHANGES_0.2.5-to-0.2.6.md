## Review these sections

- **audit-table-reads-as-four-kinds-of-row** - 0.2.6 changes what you SEE, and that half travels with /plugin update rather than with this migration: the audit-table renderer and the doctrine your session reads are the payload's own scripts/, docs/ and skills/, which the plugin update replaces wholesale. The table used to arrive as nine rows in one stream - your four roles, the three review classes, the fact-check gate and R1 - so an empty cell in it looked the same whether it was structural or a setting nobody had filled in. It now prints as four labelled blocks under the same header: '-- roles (who does the work) --', '-- review classes (what gets audited, how many passes) --', '-- always-on gate --' and '-- routes --'. Every value, every marker and every column is byte-for-byte what it was: nothing about who audits what, on which engine, with how many passes has moved, and `/pnp:roles --set` still changes exactly the rows it changed before - the review classes and the roles. What the blocks buy is that the two rows nothing configures now say so by position rather than by a dash you have to interpret: the fact-check gate runs before every paid pass and has no setting at all, and R1 has no auditor by definition. Neither of them is a row you forgot to configure, and neither may go missing - a session re-rendering the table from memory dropped both of them silently, which is what the self-check now pins with a control. The same release also asks the two skills that show you the table - /pnp:work at its tree check, /pnp:setup after an install - to print the tool's literal output rather than a retelling of it, which /pnp:mission and /pnp:roles already did. Nothing here changes a value in your aiwf.config.json: the table is a rendering of the settings you already have, and it is read with `/pnp:roles` on the project itself.
