## Review these sections

- **git-verb-gate** - 0.2.2 adds a third enforcement hook - Gate 4, on the Bash tool. It refuses an ask-class git verb (commit, push, reset, checkout, ...) to any subagent that is not the Writer, because a background agent's permission dialog never reaches you. For the session itself it raises a dialog only on the git forms your ask rules never spell out: `git.exe <verb>` for anything but push/merge/rebase, any `git -C <path> <verb>` (your rule names the project root, and a hook that reads no project directory cannot confirm a path), a wrapper Claude Code does not strip such as `sudo` or `npx`, and irregular whitespace between the tokens. Those matched no rule and raised nothing at all before. Everything the harness already gates by itself stays silent - Claude Code's permission documentation describes a matcher that tests your rules against each subcommand of a chained command and past `timeout`/`nice`-style wrappers and `NAME=value` prefixes - so ordinary usage gains no new click, and where a rule does match, a hook ask and a rule ask are one dialog rather than two. One limit is worth knowing before you rely on any of it: this hook is wired on the Bash tool and every rule in your ask list is a `Bash(...)` rule, so if your harness exposes a second shell tool - a Windows session carries a PowerShell tool next to Bash - the same git verbs run through THAT tool reach neither layer and raise no dialog at all. It needs no unusual command form, only the other tool, so a subagent with a broad tool allowlist can get past the deny by choosing it. It is payload code delivered by the plugin update itself: this migration touches nothing in your project - no config key, no managed region, no ask rule, no agent file. There is nothing for you to do; the CHANGELOG entry is the whole story
