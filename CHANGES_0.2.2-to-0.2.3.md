## Review these sections

- **powershell-ask-ruleset** - 0.2.3 closes the second shell tool. A permission rule is addressed to a TOOL, and a Windows session carries a `PowerShell` tool next to `Bash` - so a list of `Bash(...)` rules gated commit, push, merge, rebase, reset and every destructive command on one tool and left the other one wide open, and Gate 4 was wired on `Bash` alone. This migration adds the mirror: for every `Bash(<X>)` ask rule the payload ships, a `PowerShell(<X>)` rule with the same command prefix, 54 of them, plus `PowerShell(*)` next to `Bash(*)` in the factory allow posture. Gate 4 now runs on matcher `Bash|PowerShell` and judges each command in its own tool's dialect - PowerShell splits subcommands on `;`, `|`, `&&` and `||`, `&` is its call operator rather than a separator, no wrapper or `NAME=value` stripping is documented for it, and its matching is case-insensitive - and every one of those differences is resolved towards raising a dialog rather than staying silent, so on PowerShell you may see a prompt for a prefixed command such as `timeout 30 git commit` that stays silent on Bash. WHAT THIS DOES TO YOUR settings.json: the 54 mirror rules are ADDED where they are missing, exactly like any other payload rule - a rule you added or edited yourself is never touched, and a rule you deliberately removed stays removed (its tombstone still holds). The allow/deny posture is not rewritten: `PowerShell(*)` reaches only a project that had no permissions block of its own when it was set up. If your session has no PowerShell tool the new rules are inert - they are prefix matches on a tool that never appears, the same argument that already lets one OS-neutral ruleset ship the Windows and the POSIX delete commands side by side. `Monitor` needs no rules of its own: it runs its commands under the Bash ones. What is still outside both layers is a tool NEITHER of them names - stated as a class in docs/LOOP.md rather than as a promise
