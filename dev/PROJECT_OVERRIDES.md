## Identity

We are building **PromptAndPray** - the pnp Claude Code plugin - a disciplined four-role working loop with native operator gates; this repository is the plugin itself, self-installed so its own development runs under the loop it ships.

PromptAndPray is **not**:

- **the product it was extracted from.** That project is a *consumer* (installs `pnp@promptandpray`
  from this repo as a local marketplace, project scope). Its name, operator language and paths never
  enter the payload - the provenance section of the self-check is the gate; only `dev/` may hold them.
- **a Codex plugin, or a wrapper around one.** Reviewer/QA are engine-neutral; the official Codex
  plugin is a second opinion next to this loop, not a component of it.
- **a runtime / state machine.** No counters, no lock files, no external service: convention plus
  the three PreToolUse hooks plus native permission dialogs. A feature that needs a daemon is out of
  scope.
- **advice.** Every operator gate that CAN be a native dialog IS one; a rule living only in a
  document where a hook or an ask-rule could carry it is a defect.

## Hard rules

- Never run destructive Git or filesystem cleanup commands, and never touch, move, or delete
  untracked operator work or legacy files, unless the operator explicitly asks for that exact
  operation immediately before it runs. This project's destructive / system-changing class:
  - `git push` / merge / rebase to this repo or a consumer project (separate word each; the
    release-tag push rides the tag word);
  - removing anything under `docs/` (only through a migration that names it);
  - `--confirm-remove-stale` on `/pnp:setup`, and `/plugin uninstall` in a consumer project.
- Do not change files outside the requested scope.
- Do not start long-running services (there are none); a `claude` session started to observe a gate
  live is the operator's, never an agent's.
- **Prose in the payload is R1; code goes through the Writer** (operator decision 2026-10-16).
  Prose - `docs/`, `skills/`, the text of `templates/`, `README.md`, `CHANGELOG.md` - is edited in the
  main session: edit, provenance grep, `validate-payload`, commit; no Writer, no auditor, no plan, no
  readiness. Code - `scripts/`, `hooks/`, `schema/`, `.claude-plugin/` - goes through the Writer; a
  Codex pass over code only on the operator's word. `dev/` and the self-install layer (`.claude/`,
  root `CLAUDE.md`) are R1.
- **Release discipline** (operator decision 2026-10-16, corrected 2026-10-18). Every payload change
  that must reach a consumer is a release: a version bump + a migration + a `CHANGELOG.md` block - a
  structural change carries its real ops, a prose-only change one `note` op - because a consumer's
  `/plugin update` refreshes NOTHING at the same version (verified 2026-10-18: the marketplace clone
  moved, the version-keyed cache `~/.claude/plugins/cache/promptandpray/pnp/<version>/` did not;
  REL-032). A release cuts the bump in
  `.claude-plugin/plugin.json` and the `CHANGELOG.md` block (ending `Retires local rules:`). The tag is
  created LOCALLY on the record commit and pushed WITH `main` in ONE push - two words (tag, push),
  one dialog; CI is not waited for (operator rule 2026-10-02): a version is released when that push
  lands, and a red POSIX leg is a defect ticket, not a release block. A consumer picks the version up
  only through `/plugin update` + `/pnp:update`. (product)
- **Provenance.** `git grep -nP "[\x{0400}-\x{04FF}]" -- docs skills templates scripts schema hooks
  migrations` is empty before every commit - for a prose-only diff that grep IS the gate; the
  self-check's provenance section runs when the diff touches scripts/, hooks/, templates/ or schema/
  (§ Test policy), and a new allowlist entry needs the one file that justifies it.
- **No AI attribution in git** (operator rule 2026-08-31). No Co-Authored-By, Claude-Session,
  session URL or "Generated by" line in any commit message, trailer or PR text, COO and Writer alike,
  in every one of the operator's repositories; the harness attribution reminder is overridden; every
  Writer brief carries the line. (product)

## Product direction

The first value loop: **a project installs the plugin, runs one R2 ticket through Writer -> Reviewer
-> commit gate with every gate a native dialog, then takes a newer version through
`/plugin update` + `/pnp:update` without losing its own voice.** A proposed change that does not make
install, loop or update more correct, more honest about its guarantees, or provable by the
self-check is not this project's next step. Publishing to other users comes only after the update
path is proven on the consumer (P8).

## Architecture direction

Stack: Node.js (zero dependencies), PowerShell + bash wrappers, Claude Code plugin (skills, hooks, agents, templates, migrations)

Boundaries a reviewer checks:

- **Three layers, and who writes what.** Payload (`docs/ skills/ templates/ scripts/ schema/
  hooks/ migrations/ examples/ .claude-plugin/`) -> project layer rendered by setup/update
  (`.claude/aiwf-native/*`, `.claude/agents/*`, the managed `CLAUDE.md` region, the owned ask-rules
  in `.claude/settings.json`) -> operator-owned content (the overrides doc after its seeding,
  everything outside the `aiwf-core` markers, foreign permission rules). The payload's engines
  WRITE only the managed artifacts, under the two-hash bookkeeping (no silent overwrite, no delete
  without `--confirm-remove-stale`), never the operator-owned content. The hooks READ the project's
  `aiwf.config.json`, `roles.json`, the active PLANs (Gate 2 off-plan), the files a plan-class
  reviewer brief names (Gate 2, through `scripts/engine/plan-gate.js`) and `.aiwf/route-state.json`
  (Gate 3) - nothing else; Gate 4 reads nothing beyond its payload. Nothing in the project layer ever
  writes the payload.
- **`schema/aiwf.config.schema.json` is the single authority for the config shape**; the interview,
  the generator and the self-check derive from it, never restate it.
- **The hooks fail in the safe direction, per gate** (`docs/LOOP.md` § Enforcement of Writer-only
  writes): Gates 1, 3 and 4 DENY, Gate 2 ASKS (and DENIES a failing plan-class Claude pass), any
  unexpected error inside Gate 2 resolves to ASK. A change that flips a fail direction is R3.
- **Zero runtime dependencies.** No `node_modules`, no build step; the wrappers are PowerShell 5.1
  ASCII-only / bash LF-only and mirror each other flag for flag.
- **The self-check executes real entrypoints** (hooks, resolver, validators) and every assertion has
  a negative control or is printed as `[NOTE]` with its reason.
- **`dev/` is not payload** and may hold what the payload may not (operator language, machine paths).

## Data, tenancy and access control

- No database, no tenants. "Migrations" are **payload migrations** for installed projects: one
  manifest `migrations/index.json` (ordered, monotonic in version, last entry = the payload version)
  plus one directory `migrations/NNNN_<slug>/` per migration holding `ops.json` and `NOTES.md`,
  validated by `scripts/update/validate-payload.mjs` and applied by the update engine
  (`scripts/update/`) with a write-ahead journal. The op vocabulary is `add-config-key`,
  `rerender-managed-region`, `reconcile-ask-ruleset`, `note`, `seed-file` (written only when absent,
  never recorded; RBA-001) - nothing else, and no migration ever deletes an operator file.
- Access control is the **permission ask-ruleset** (`templates/settings.ask-ruleset.json`): a rule
  added there is a managed-artifact change (migration + bump); a rule removed there ships with a
  `reconcile-ask-ruleset` op so consumers lose only what they never edited.

## Test policy

The single home of the test policy is this section plus the acceptance suites
(`scripts/setup/test-setup.mjs`, `scripts/update/test-update.mjs`,
`scripts/selfcheck/aiwf-selfcheck.js`, `scripts/spike/run-spikes.mjs`,
`scripts/ci/run-example-cycle.mjs`). Routing:

- pure logic / helper / transform / validation / format -> targeted unit tests;
- E2E only for a business result through server + browser that cannot be proven otherwise (data
  written and read back, permissions visible in the UI, a server-decided redirect, server-computed
  values, integrations) - never a visual property, a text or "the page loads" (operator rule
  2026-10-05); this project has no E2E runner: runtime behaviour is proven by the self-check and
  spike probes; (product)
- mixed change -> both where applicable;
- a missing obvious proof test is a scope miss.

The literal VERIFY commands live in `aiwf.config.json` `verify.commands`: `validate-payload`,
`setup-suite`, `update-suite`, `example-cycle-windows`, `example-cycle-linux`, `selfcheck`, `spikes`,
`plugin-validate`.

**VERIFY is proportional to the change** (operator rules 2026-09-24, 2026-10-17). A change owes
only what its diff can break, run ONCE:
- prose, skills, docs, templates, README, CHANGELOG -> NO suite: the provenance grep (`git grep -nP
  "[\x{0400}-\x{04FF}]" -- docs skills templates scripts schema hooks migrations examples README.md`)
  + `validate-payload`; a template change adds one render dry-run on a scratch copy;
- schema / config / roles -> `selfcheck`, `validate-payload`, `setup-suite`;
- update engine / migrations -> `update-suite`, `validate-payload`, `selfcheck`;
- hooks / gates -> `selfcheck`, `spikes`;
- `scripts/ci/` or `examples/` -> the example cycle too;
- a release that carries only prose (a `note` migration + the bump; operator word 2026-10-18 „не ми се
  чака целия верифай") -> `validate-payload` + the self-install `/pnp:update --apply` on this repository
  with its embedded self-check; NO suite locally - CI runs the full set after the push.
A diff spanning several rows runs their union; nothing beyond the ticket's own rows runs locally
(operator rule 2026-09-28, HARD-021), and no row runs twice. CI runs the full set on the pushed
commit, after the fact, on `windows` and `ubuntu`. (product)

**VERIFY runs in PORTIONS** (operator rules 2026-09-17, 2026-09-19, 2026-09-22). Portion 1: the
eight Windows commands as ONE parallel batch. Portion 2: the POSIX suites under WSL (user `pnp`) as
ONE invocation with its legs SEQUENTIAL inside it, started only AFTER Portion 1 has finished - never
concurrent with it (the two together exhaust the machine's memory). Every Writer brief states the
portions in those words. Portion 2 is NOT a release gate (operator rule 2026-09-28, HARD-021): it is the local reproduction
path when a POSIX CI leg goes red. (machine)

**The operational runbook is `dev/VERIFY_RUNBOOK.md`** (operator rule 2026-09-22): command shapes
and every recorded trap; every brief that runs VERIFY carries the pointer, and a red test on a trap
described there is a defect of the brief. (machine)

The row's suite runs ONCE, started by the COO in the background at the Writer's handoff, in parallel
with the diff read; a fresh scan agent only when the COO cannot run it. Never a second batch. Logs of
any run go OUTSIDE the repository (the example cycle asserts a byte-identical tree). No micro-round
edits while a suite is running (RBA-001). (operator rule 2026-10-17)

**Independent units run in parallel by default** (operator rules 2026-10-02, 2026-10-05) -
independent steps, large mechanical Writer work split across Writers from the dispatch, a scan
beside an auditor pass - subject to the portions rule above.

## Environment

cross-platform tool.

**COO context source** (machine-local, the operator's own statusline `~/.claude/statusline.sh`): it
writes `~/.claude/ctx/<session id>.pct` (used percent) and `.size` (window tokens) for every session
on this machine; the COO context is `pct * size / 100` - the number the statusline itself prints,

the machine source `/pnp:plan` and the record skeleton read; nothing of it is payload. (machine)

(observed 2026-10-23, 0.3.5: applied, self-check 1368/1368). Never ask the operator to switch auto mode
off for an apply. The payload sentence that says otherwise is a ROADMAP § DOCTR item. (machine)

## Loop shape (this project's overrides of the generic defaults)

Shape parameters only; the gates are payload mechanics (`docs/WORKFLOW.md` § Loop shape and its
overrides). Correction-round cap: `loop.correctionRoundsCap` = 2.

- **COO routing tiers** (operator rule 2026-10-15): top = Fable, cheap = **Opus**, never a Sonnet
  COO; the Writer gets no recommendation. (product)
- **Gate checkpoint hook** (operator rule 2026-10-14; HARD-024). The COO rewrites
  `.aiwf/checkpoint.md` WHOLE (Write, not an append; <= 60 lines: state, operator decisions, live
  agents, next steps, "After compaction do") at every gate - dispatch, handoff, verdict, before a
  commit - and when the hook `.claude/hooks/context-gate.mjs` reports >= 950k tokens of context; at
  >= 1000k IMMEDIATELY, after the current step. The hook takes no value and stays silent without the
  statusline's `~/.claude/ctx/` files; after compaction it returns the checkpoint to the context, and
  the COO reads only it and the files it names. The ticket and session boundary is the payload's
  session rule (`docs/WORKFLOW.md` § Plan readiness review).
  *Expires* when the payload carries the mechanism (candidate: CANDIDATES § „Таван на контекста“).
  (product)
- **Ticket-end cleanup** (operator rule 2026-10-06, widened 2026-10-16): everything the ticket
  created under `.aiwf/` is deleted with no chat question (the delete dialog is the gate), after
  anything worth keeping moved to `readiness/<ABBR>/` or the record.
