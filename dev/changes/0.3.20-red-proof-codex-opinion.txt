On draft point **(1), change**. Keep the focus on changed behaviour, but replace categorical exemptions for shape, type and message tests with a material-risk test. A missing propagated field or `{plate}` placeholder can break the promised behaviour; key adjacency or redundant shape assertions generally justify less proof effort. The opened logs demonstrate both kinds of checks. Classification by filename or assertion syntax would discard useful protection. See [field proof:21](D:/Stratex/dev/backlogs/readiness/TRM/TRM-002/TRM-002-r1-red-A-11.log:21), [placeholder proof:16](D:/Stratex/dev/backlogs/readiness/TRM/TRM-002/TRM-002-unit-red-C-8.log:16), and [key-position check:25](D:/Stratex/dev/backlogs/readiness/TRM/TRM-002/TRM-002-r1-red-C-6.log:25).

On **(2), change**. Keep batching and build reuse; drop “one build with all faults” as an absolute. TRM-002 itself shows why: an early failure can conceal later checks, and a preview fault need not exercise persistence. Batch faults only when the required assertions remain reachable and their failures attributable. Require an additional expensive round only for a named material proof gap that remains.

On **(3), change**. Keep deterministic setup for an E2E whose subject begins after AI mapping. A recording or fixed mapping setup should preserve the downstream production path being tested. Drop “never live”: a separately scoped test of the provider integration may legitimately require it. Here, the final scoped failure stopped at Step 2, and the recorded correction mapped the missing field manually before one focused successful rerun. That supports removing unrelated AI variability from this plate-display proof. See [final-run failure:54](D:/Stratex/dev/backlogs/readiness/TRM/TRM-002/TRM-002-r2-verify-e2e.log:54), [correction account:43](D:/Stratex/dev/backlogs/readiness/TRM/TRM-002/TRM-002-review-brief-pass3.txt:43), and [focused result:24](D:/Stratex/dev/backlogs/readiness/TRM/TRM-002/TRM-002-r2-e2e-step3.log:24).

On **(4), drop the automatic-closure formulation**. “No code defect found” does not make missing proof harmless. A permissive comparison or an untested persistence boundary can prevent justified completion without an observed production failure. However, missing *redundant* red records should be notes and should not generate another correction or paid audit round. The distinction must be material proof adequacy, not whether the finding is labelled “test evidence.”

My proposed replacement for the blanket red requirement is exactly:

> Require red/green sensitivity evidence for representative tests of changed or corrected acceptance behaviours whose failure meets the brief’s blocking threshold. Name the failure modes and proof surfaces in the brief. For each mode, retain a relevant assertion failing on the old behaviour or a named plausible fault, then passing after correction or restoration, using production code or a production helper. Failure before the relevant assertion does not qualify. Evidence may be shared across tests when it demonstrates their claimed failure mode. Use the least costly layer that proves the property; require higher-layer sensitivity evidence only for a material boundary the lower-layer proof does not exercise. An additional demand must identify a concrete uncovered contract failure at the brief’s threshold. Missing sensitivity evidence blocks only where that material proof remains absent.

Its exact suppression dual is:

> Do not require a separate mutation, red/green pair, build or audit round merely because a test or assertion was added or changed, checks shape, types, keys or text, or duplicates an already demonstrated failure mode. Do not repeat accepted sensitivity evidence while its relevant assertion and exercised production path remain unchanged. These omissions do not waive ordinary test execution, acceptance proof, investigation of failures or justification for changed expectations.

For Silerax, I would pair that with this exact addition:

> Batch E2E faults only when they cannot mask the required assertions. An additional red build must name the material end-to-end failure still unproven and explain why existing evidence or a cheaper test cannot prove it. For acceptance beginning after AI mapping, use deterministic recorded provider output or fixed mapping setup while retaining the downstream production path. Use a live provider only when the acceptance explicitly includes that integration.

Its suppression dual is:

> Do not add E2E red rounds for behaviour already proven at an adequate lower layer, rebuild without a relevant source change, repeat retained final-build evidence, or invoke live AI merely to prepare a downstream test.

The general sensitivity rule belongs in the **PromptAndPray payload**, because the unconditional new-test obligation originates there. The E2E build economy and AI setup provision belong in **Silerax project additions**, where their costs and testing boundaries are established. Silerax already routes helpers and i18n keys to targeted units and restricts E2E to business results requiring server plus browser; this proposal follows that existing distinction.
